## 合并总纲（先立规矩）

**官方锚点（2026-08-10 赛道报名公告原文）**：
> 「一个场景清晰、流程顺畅、证据完整的小闭环，远比一个功能庞杂却难以运行的大平台更有说服力。」

由此确立合并四原则：

1. **合并发生在叙事层与架构层，不发生在 Demo 层**——大项目=大叙事+统一对象模型；复赛 Demo 仍是单场景单链路小闭环。
2. **同骨架合并**：共享"异常→根因→行动→沉淀"对象模型的合并（E/F/G/A 同骨架）。
3. **同数据域合并**：吃同一批数据的模块合并，避免重复建设（C 并入计划域；H 作数据底座暗线）。
4. **叙事不打架不合**：厂内运营视角与厂商售后视角用户不同，不合为一个"四不像"。

## 合并结果：3 个大项目（P1/P2 主推，P3 备选）

### P1「厂内异常闭环中枢」Factory Ops Copilot（厂内视角）★主推

- **合并件**：E 质量根因+8D（96，主发动机）＋ F Andon 响应（88，响应骨架）＋ G 点检多模态（85，感知入口）＋ D/H 数据底座（87/68，暗线模块）＋ C 的"缺料→请购"动作模块
- **统一叙事（一段话）**：制造现场每天产生大量异常信号——设备报警、质量超标、点检异常、缺料预警。它们的归宿本应是同一条链：**发现 → 分诊 → 根因 → 行动 → 沉淀**；今天这条链散落在人、微信群和四套系统里，且每次处理完知识即蒸发。我们以"异常"为统一对象模型构建 Agent 中枢：多模态入口发现异常，数据侦探做多源归因，行动代理产出工单/请购动作包，沉淀代理把每次异常变成可复用的工厂记忆。
- **官方六要素覆盖**：设备、质量、工单、库存（4/6，供应链部分覆盖）→ 官方5方向映射：#1+#2+#3
- **个性化评审对位**：多源信息融合=根因阶段四源对齐；流程闭环=告警到工单全程；解释性=证据链+置信度；可操作性=动作包；安全边界=停线建议人工确认
- **赛事 MVP 点（三档）**：
  - **初赛 MVP（8.16 前，仅材料）**：叙事 PPT：痛点→统一对象模型架构图→一条质量异常案例故事线（线框/示意图即可）＋500 字简介
  - **复赛 MVP（9.3 前，可运行）**：**只做质量一条链**——SPC 告警 → 数据侦探（批次谱系×工艺参数×设备状态×来料）→ 根因证据链 → 8D 初稿 → 工单生成。数据：UCI SECOM + 自建多表模拟集（模拟逻辑写入合规文档）
  - **决赛展示 MVP（9.22，扩展留白）**：Andon 事件流面板（F）｜点检照片入口（G）｜缺料请购联动（C 模块）——按进度选展
  - **明确不做（范围红线）**：真实设备控制、排产最优化（归 P3，避免叙事稀释）、全要素平台化演示
- **风险与对策**：评委质疑"范围大"→ 答辩口径「平台是叙事，交付是单链闭环」；归因准确性→ 注入式 ground truth 评测自证
- **细节后置清单（PRD 阶段再定）**：Agent 间消息协议、工具清单、数据 schema 字段级设计、评测集规模、UI 形态

### P2「装备售后全旅程闭环」After-Sales Copilot（厂商视角）★主推

- **合并件**：A 售后技术支持（92，主发动机）＋ G 照片报修入口（85）＋ H 装机/验收文档结构化（87，设备档案模块）＋ E 复盘变体（批次性故障→售后 8D→工程变更建议）＋ F 的工单跟踪模块
- **统一叙事（一段话）**：装备制造商的售后是一座"散落在客户现场的隐形工厂"：报修靠电话微信、诊断靠专家出差、备件靠翻表格、修完知识就蒸发。我们做一个从"客户报修"到"厂商知识资产"的全旅程 Agent：多模态报修 → 多轮问诊 → 手册/历史案例检索 → 备件与工单 → 维修指导 → 案例沉淀回流；延伸闭环：批次性故障自动触发售后质量复盘（8D），反哺工程变更与下一代产品设计。
- **官方六要素覆盖**：设备、工单、库存（备件）（3/6）→ 映射 #1+#3
- **个性化评审对位**：多源融合=手册×故障码×历史工单×照片；闭环=报修到沉淀；解释性=诊断证据+案例引用；可操作性=工单+备件下单；安全边界=高危操作分级提示、持证人员引导
- **赛事 MVP 点（三档）**：
  - **初赛 MVP**：双端故事（客户报修端+工程师工作台）叙事 PPT＋一条完整报修-修复-沉淀旅程故事线
  - **复赛 MVP**：报修（照片）→ 多轮问诊 → 诊断（手册 RAG+工单 CBR）→ 备件查询 → 工单生成 → 案例回写。数据：自建 2-3 本模拟手册（规避版权）+200 条模拟工单
  - **决赛扩展留白**：装机验收文档→设备档案自动建立（H）｜批次故障复盘（E 变体）
  - **明确不做**：真实厂商系统对接、远程控制类功能
- **风险与对策**："维修问答机"竞品拥挤 → 差异化三件套必须显性：工单/备件动作闭环、案例沉淀飞轮、双端产品形态
- **细节后置清单**：故障树 DSL 规范、案例库 schema、CBR 检索策略、双端信息架构

### P3「从订单到齐套的计划协同」Planning Copilot（备选）

- **合并件**：B 材料排产（85.5，主发动机）＋ C 采购计划（81.5，采购联动模块）＋ H 供数暗线
- **统一叙事**：中小厂计划员的一天：订单进来→齐套检查→排产建议→缺料请购→供应商交期风险。传统 APS 买不起也用不动；通用 LLM 算不准也不敢信。我们做"LLM×求解器"分工的计划副驾：**求解器管最优化，LLM 管交互、澄清与解释**——尤其是插单时"为什么这单被延后、缺哪个料、有什么替代方案"的冲突解释。
- **合并增益**：C 并入后 B 的最大扣分项（交付物是表而非动作）被修复——交付物升级为"动作包"（工单建议+请购单+交期承诺草案），闭环分 3.5→4.5，合并后估分 ~88-90
- **赛事 MVP 点**：初赛=叙事+架构（LLM/求解器契约图）；复赛=齐套核算+插单冲突解释一条链（自建模拟数据：3 层 BOM×库存×在途×订单 30-50 单）；决赛留白=供应商风险看板
- **定位**：第三备选。若 P1/P2 任一推进受阻再启用；其"库存/供应商"模块随时可反哺 P1 的行动层
